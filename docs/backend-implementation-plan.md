# План реализации Python бэкенда

Цель первой поставки — через API или CLI запустить воспроизводимое сравнение линейной регрессии MADlib и scikit-learn, пережить остановку worker и получить проверенные результаты. Архитектурные контракты описаны в [архитектуре](backend-architecture.md). Этапы ниже последовательны; сроки зависят прежде всего от сборки MADlib-образа и согласования алгоритмов.

## Этап 0 Проверка экспериментального стенда

Текущий статус реализации (21 октября 2026): стенд проходит 60 штатных MADlib install-check; версии датасетов, матрица и оба адаптера линейной регрессии реализованы. Этапы ниже описывают целевую полноту: CPU/RAM sampler, парная статистика и рекомендации реализованы; автоматический retry, cleanup/retention и контрольные серии влияния мониторинга ещё предстоят. Практические команды и точные ограничения — в [development.md](development.md), результаты проверок — в [validation.md](validation.md).

Собрать PostgreSQL 15.x + MADlib 2.1.0, выполнить штатную проверку установки и минимальные train/predict на синтетической таблице. В Python 3.12 проверить совместимую зафиксированную версию scikit-learn и её линейную регрессию. Зафиксировать objective, intercept, dtype и допустимые численные различия. Проверить сбор ресурсных метрик внутри Linux-контейнеров.

Результат: Dockerfile/Compose для bench DB, smoke SQL, lock зависимостей приложения, таблица capabilities, пример согласованных параметров. Готовность: обе модели обучаются и дают конечные предсказания с сопоставимым качеством на одинаковых строках. До этого этапа не обещать поддержку дополнительных алгоритмов.

## Этап 1 Каркас приложения и метаданные

Создать pyproject, src-layout, конфигурацию окружения, структурированные логи, FastAPI app и CLI. Реализовать domain-типы и переходы состояний; добавить модели metadata, Alembic и repositories/UoW. Поднять metadata-db, api, worker и migrate. Разделить подключения metadata и bench DB.

Результат: запускаемое приложение, миграции, health endpoints и создание experiment draft. Готовность: чистая БД мигрируется; невалидный spec отклоняется; сохранённый spec возвращается без потери полей и имеет schema_version/config_hash. Миграция запускается отдельной командой, а не каждым API-процессом одновременно.

## Этап 2 Очередь и жизненный цикл worker

Реализовать job repository с SKIP LOCKED, lease, heartbeat, token, benchmark_slot и supervisor. Сначала использовать тестовый executor с управляемыми длительностью, ошибкой и зависанием. Добавить start/cancel API, idempotency keys, recovery, backoff и историю attempts.

Результат: рабочий цикл queued → running → terminal без ML. Готовность: два worker не принимают один job одновременно; устаревшая попытка не публикует результат; перезапуск восстанавливает задание; неизвестное состояние старой нагрузки изолирует слот; отмена останавливает дерево процессов. Эти проверки выполняются на настоящем PostgreSQL, а не SQLite.

## Этап 3 Версии данных и общая подготовка

Реализовать регистрацию разрешённых таблиц, materialized snapshots, профиль и стабильный row_id. Добавить сохранённое train/test-разбиение, ordered feature schema, prepared_dataset и manifest. MVP принимает числовые данные без пропусков. Неподдерживаемые типы и целевой столбец в признаках отклоняются.

Результат: оба адаптера получают одну immutable версию данных. Готовность: train/test не пересекаются; повторное использование версии сохраняет те же row_id; изменение источника не меняет snapshot; одинаковый рецепт повторно использует готовую подготовку по ключу версии и конфигурации. Учесть активные ссылки перед cleanup.

## Этап 4 Вертикальный сценарий scikit-learn

Реализовать BackendAdapter, RunContext и типизированные ссылки на модель/предсказания. Добавить чтение признаков через psycopg, оценку памяти, estimator factory для линейной регрессии, ограничение потоков, train/predict, запись предсказаний и модели. Подключить таймеры фаз и базовый evaluator RMSE/MAE.

Результат: полный путь API → очередь → executor → результат для Python. Готовность: результат соответствует тестовой выборке по row_id, модель и manifest доступны через API, длительность загрузки отделена от fit, объём сверх лимита отклоняется предсказуемо.

## Этап 5 Адаптер MADlib и парное сравнение

Реализовать безопасные SQL-шаблоны линейной регрессии, модельные таблицы, предсказания, диагностику и cleanup. Добавить statement_timeout, регистрацию сессии, отмену SQL и проверку её завершения. Планировщик создаёт пары запусков с сохранённым порядком, warmup и измеряемыми повторами.

Результат: один case выполняется обоими backend и создаёт одинаковый контракт predictions. Готовность: на синтетической задаче проверены качество и допустимые численные расхождения; перестановка строк не меняет оценку; одновременно на стенде выполняется одна нагрузка; прерванный MADlib-запрос не продолжает работать перед следующим экспериментом.

## Этап 6 Ресурсы и воспроизводимость

Добавить psutil sampler, cgroup/container measurements и environment snapshot. Зафиксировать границы model_wall_ns, train_wall_ns, common_prepare и полного времени. Записывать лимиты памяти/CPU, настройки потоков, policy кеша, число повторов и пропущенные сэмплы. Вынести частоту мониторинга в конфигурацию.

Результат: сравнимый отчёт по фазам и раздельным областям ресурсов. Готовность: MADlib DB resources не подменены ресурсами клиента; Python DB I/O тоже учитывается; unavailable не превращается в ноль; измерения не содержат ожидание очереди внутри train. Контрольная серия позволяет оценить влияние самого мониторинга.

## Этап 7 Рекомендация и отчёт

Реализовать парную агрегацию, ограничения качества/ресурсов, verdict и объяснение. Добавить finalize handler, публикацию JSON и CSV, API результатов и скачивания. Сохранять версии политики и конкретные attempts, использованные для вывода. HTML-отчёт возможен следующим небольшим расширением; PDF не требуется для MVP.

Результат: эксперимент завершается доступным отчётом. Готовность: неполная пара исключена с причиной; высокий разброс допускает inconclusive; повторный finalize не создаёт конфликтующих рекомендаций; падение между записью файла и metadata восстанавливается; в отчёте есть конфигурация, окружение, качество, время, ресурсы и ограничения вывода.

## Этап 8 Проверка отказов и поставка MVP

Проверить остановку worker во время train, потерю metadata DB, разрыв bench-соединения, отмену одновременно с завершением, OOM executor, SQL timeout и заполнение диска. Добавить очистку сиротских объектов с учётом lease и ссылок, описание запуска, восстановления и политики хранения. Выполнить сквозную серию через публичный API из чистого Compose-стенда.

Готовность: каждый сбой приводит к определённому состоянию; нет двух принятых результатов одной попытки, публикации от устаревшего владельца или скрыто продолжающейся нагрузки на доступном слоте. Сохранённый spec повторно запускается через CLI и создаёт новый эксперимент с теми же входными условиями. Совпадение времени до последней цифры не является критерием воспроизводимости.

## Расширение после MVP

| Приоритет | Возможность | Предусловие |
| --- | --- | --- |
| P1 | Бинарная логистическая регрессия | Согласованные objective, regularization, probability и class mapping |
| P1 | Пропуски, scaling и категориальные признаки | Fit только на train, сохранённый рецепт, единое представление |
| P1 | Несколько размеров выборки и матрица параметров | Лимит числа runs, проверка полного плана до enqueue |
| P2 | Validation и подбор параметров | Разделение tuning и финального test |
| P2 | Дополнительные алгоритмы | Capability-тесты и честное описание различий реализаций |
| P2 | Несколько физических стендов | Независимые benchmark_slot и ресурсные границы |
| P2 | SSE и интеграция frontend | Стабильные event/API schemas |
| P3 | Объектное хранилище и отдельный брокер | Подтверждённая потребность в масштабе, сохранение идемпотентности |

## Проверки по уровням

| Уровень | Что проверять |
| --- | --- |
| Unit | Переходы состояний, построение матрицы, нормализация spec, критерии рекомендаций, метрики на известных значениях |
| Integration с metadata PostgreSQL | Конкурентный захват, истечение lease, fencing, идемпотентность, миграции, гонка cancel/complete |
| Integration с bench PostgreSQL и MADlib | Реальный SQL train/predict, права, транзакции, отмена, cleanup только своих объектов |
| Contract | Оба адаптера дают допустимые ModelRef/PredictionRef и согласованный набор row_id |
| E2E | Создание → запуск → результаты → отчёт; отмена; восстановление после аварии |
| Методические | Один split, одинаковые признаки, отсутствие test leakage, парные повторы, корректные границы измерений |

Тесты не требуют равенства коэффициентов разных solver до последнего знака и не фиксируют абсолютное время выполнения. Качество проверяется с обоснованным допуском, конкурентность и публикация результатов — строгими инвариантами.

## Первый рабочий срез

После проверки MADlib-окружения первая реализационная задача объединяет этапы 1–2: `POST experiment`, `POST start`, очередь PostgreSQL, supervisor, тестовый subprocess, `GET status` и `POST cancel`. Этот срез проверяет основу исполнения до подключения ML. Следующий срез добавляет immutable dataset и scikit-learn, затем MADlib и парное сравнение.

Полный MVP считается готовым после этапа 8. Разделение процессов само по себе не обеспечивает надёжность: обязательны проверенное восстановление, контроль старой нагрузки и единая методика измерений.
