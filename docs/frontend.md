# Frontend: Vue и Yarn

Интерфейс реализован на Vue 3 (Composition API), TypeScript, Vue Router и Vite. Пакетный менеджер — Yarn Classic 1.22.22; точные зависимости закреплены в frontend/yarn.lock. Для разработки используется Node 24. Шрифты Golos Text поставляются локально с приложением; обращения к внешним сервисам для отображения UI не нужны.

## Запуск через Docker

Из корня репозитория:

```powershell
docker compose --profile bench up -d --build bench-db
docker compose up -d --build api worker frontend
```

Откройте http://localhost:8080. Для существующей bench-БД должна быть установлена функция мониторинга по [инструкции](measurement-and-recommendations.md). Данные уже работающего стенда сохраняются.

Frontend собирается Yarn в многоэтапном Dockerfile, Nginx раздаёт статику и проксирует /api и /health на FastAPI. API и frontend имеют один origin; отдельная настройка CORS не нужна. Прямые переходы и обновления вложенных маршрутов поддержаны через SPA fallback. Локальные порты привязаны к 127.0.0.1.

## Разработка

Сначала запустите backend через Compose, затем:

```powershell
cd frontend
yarn install --frozen-lockfile
yarn dev
```

Dev-интерфейс: http://127.0.0.1:5173. Vite проксирует запросы к API на http://127.0.0.1:8000. Для другого адреса задайте API_PROXY_TARGET до yarn dev. Сборка: `yarn build`; форматирование: `yarn format`. `yarn preview` предназначен для просмотра собранной статики; API-прокси настроен именно для dev-сервера, полный production-сценарий проверяйте через Compose/Nginx.

## Пользовательский сценарий

1. Открыть «Новое сравнение» и перетащить CSV, выбрать файл или нажать «Попробовать пример».
2. При необходимости указать кодировку и разделитель. Нажать «Загрузить и проверить».
3. Дождаться проверки всех строк, просмотреть первые 10 строк и выбрать цель и признаки.
4. Нажать «Продолжить». Снимок выбранных данных создаётся автоматически; одинаковая конфигурация использует уже готовый снимок.
5. Проверить сводку. По умолчанию: линейная регрессия, оба подхода, 5 измеряемых повторов, 1 прогрев, 20% для проверки. Остальные параметры находятся в «Расширенных настройках».
6. Нажать «Запустить сравнение»: проверка, создание и постановка в очередь выполняются одним запросом с ключом идемпотентности.
7. Просмотреть рекомендацию, время, качество и ресурсы; скачать JSON-отчёт или повторить сравнение с другими настройками.

«Мои данные» хранит файлы и таблицы PostgreSQL. Обновление файла создаёт новую загрузку внутри того же источника. Старые сравнения сохраняют прежние данные и выбор столбцов. Для PostgreSQL есть «Обновить данные из таблицы». Ручное создание версии больше не требуется. В подробностях доступны история обновлений и подготовленные конфигурации.

Черновик мастера, идентификатор загрузки и ключ запуска сохраняются в sessionStorage вкладки. Обновление страницы восстанавливает выбранные столбцы и настройки. Успешный запуск очищает черновик. Файлы хранятся на сервере, а не в sessionStorage.

## Импорт и ограничения

CSV: без фиксированного ограничения размера файла, минимум 4 строки, 2–101 столбец. Лимит строк по умолчанию отключён (`ML_MAX_DATASET_ROWS=0`); при необходимости оператор может задать его явно. Заголовки уникальные, непустые, до 255 символов. Кодировки UTF-8 (включая BOM) и Windows-1251; разделители — запятая, точка с запятой и табуляция. Есть автоматическое определение и ручной выбор. Десятичный разделитель чисел — точка или запятая; запятая внутри ячейки трактуется как десятичный разделитель. Разделители групп разрядов не поддерживаются. Если столбцы разделены запятыми, ячейки с десятичной запятой должны быть заключены в кавычки по правилам CSV. Ячейки ограничены 4096 символами, значения в предпросмотре сокращаются до 160 символов.

Текстовые столбцы отображаются, но для текущей линейной регрессии выбираются только числовые столбцы без пропусков и бесконечных значений. Проверяется весь файл, включая строки за пределами предпросмотра. Пропуски не заполняются автоматически, категории не кодируются. XLSX пока не поддерживается.

Nginx не ограничивает размер тела запроса (`client_max_body_size 0`) и передаёт его без предварительной буферизации (`proxy_request_buffering off`, HTTP/1.1). В браузере отсутствует общий тайм-аут загрузки; сетевые тайм-ауты бездействия сохраняются. API потоково записывает тело запроса в общий том `uploads`. Worker проверяет CSV и копирует данные в отдельную таблицу bench PostgreSQL. Пользовательские заголовки не используются как SQL-идентификаторы. ID строк генерируются автоматически. Импорт выполняется через существующую очередь и не перекрывается с измерениями этого приложения.

Исходные CSV завершённых/неудачных загрузок старше `ML_UPLOAD_RETENTION_HOURS` (24 часа по умолчанию) очищаются при следующей загрузке. Активные задания защищены от очистки. Импортированные таблицы, предпросмотр, история и снимки сохраняются, поэтому повторное сравнение не зависит от временного CSV. API имеет запись в том `/uploads`, worker — только чтение.

Миграция `0004` добавляет загрузки и конфигурации столбцов; старые источники, снимки и эксперименты сохраняются. Compose запускает миграцию перед обновлёнными API и worker.

## Добавленные API

- `POST /api/v1/imports?filename=...&encoding=auto&delimiter=auto` — CSV в теле запроса; `dataset_id` связывает обновление с прежним источником. Ответ 202 с ID загрузки.
- `POST /api/v1/imports/{id}/retry` — повторная обработка сохранённого исходного файла без передачи через браузер; создаётся новая загрузка в том же источнике, старые снимки сохраняются. Если исходный CSV уже очищен, возвращается 410 с предложением загрузить его повторно.
- `GET /api/v1/imports/{id}` — состояние, профиль столбцов, предпросмотр и ошибки.
- `GET /api/v1/datasets/{id}/imports` — история загрузок, limit/offset.
- `POST /api/v1/datasets/{id}/prepare` — `{import_id, features, target}` для файла или `{}` для PostgreSQL; `{refresh: true}` обновляет снимок таблицы.
- `POST /api/v1/comparisons` — BenchmarkSpec и обязательный `Idempotency-Key`; атомарное создание и запуск.
- `GET /api/v1/experiments` — история с `data_name`, limit/offset.

Предыдущие API создания/проверки/запуска экспериментов и версий PostgreSQL остаются доступны.

## Проверки

```powershell
cd frontend
yarn build
yarn format:check
yarn test
```

В Windows тесты используют установленный Microsoft Edge. На другой платформе можно установить Chromium командой `yarn playwright install chromium`, задать PLAYWRIGHT_CHANNEL=chromium и выполнить yarn test. Тесты поднимают Vite автоматически или используют уже запущенный сервер на 5173.

Восемь Playwright-сценариев с подменённым API проверяют историю, автоматическую подготовку PostgreSQL, загрузку CSV, выбор столбцов, восстановление после перезагрузки, повтор запуска с тем же ключом, drag-and-drop, сетевые ошибки, мобильную навигацию, отмену и результаты.

Сквозная проверка с реальными API, worker, PostgreSQL/MADlib и scikit-learn (создаёт пример данных и сравнение):

```powershell
$env:LIVE_APP_URL = 'http://localhost:8080'
yarn test tests/live.spec.ts
```

Полная серверная проверка в отдельных тестовых схемах:

```powershell
docker compose --profile bench --profile bench-test build benchmark-tests
docker compose --profile bench --profile bench-test run --rm benchmark-tests
```

Историческая [серия из шести датасетов](benchmark-series-2026-10-21.md) сохраняет свои результаты. Её старый UI-скрипт `scripts/run-series.mjs` рассчитан на предыдущий интерфейс; для нового сценария используется `tests/live.spec.ts`.

## Дальнейшая работа: наборы данных около 100 ГБ

Целевой масштаб приложения — около 100 ГБ. Снятие лимита загрузки не означает готовности текущего конвейера к такому объёму. Пока сохраняются: тайм-аут обработки CSV/снимка 300 секунд; несколько проходов по CSV; копии исходника, таблицы, снимка и подготовленных выборок; расход диска и общие тайм-ауты заданий. Python-адаптер теперь читает train/test блоками, поэтому память обучения не растёт линейно с числом строк. Эти места требуют отдельного этапа архитектуры и нагрузочных проверок.

Предлагаемый порядок последующего этапа:

1. **Источники и доставка.** Сохранить перетаскивание в интерфейсе, но передавать файл частями с контрольными суммами, продолжением после обрыва и независимой от вкладки серверной сессией. Для данных, уже расположенных рядом с сервером, добавить подключение файла/каталога или таблицы без повторной передачи через браузер.
2. **Обработка.** Построить потоковый импорт с контрольными точками и прогрессом по байтам/строкам. Исключить повторные полные проходы только ради предпросмотра; окончательная проверка всех данных выполняется в фоне. Настройки времени обработки отделить от тайм-аутов измерений модели.
3. **Хранение и воспроизводимость.** Хранить неизменяемый источник один раз; конфигурации столбцов, разбиение и ссылки на данные записывать в манифест. Минимизировать материализацию отдельных копий; изменяемые внешние источники требуют фиксации состояния или проверяемого отпечатка. Оценивать свободный диск с учётом импорта, индексов, временных файлов и журналов PostgreSQL.
4. **Модели и честность сравнения.** Python использует потоковое центрированное QR-разложение и решение обычной задачи наименьших квадратов через scikit-learn. Все выбранные строки участвуют в обучении; SGD и подвыборка автоматически не применяются. Режим и версия решателя записываются в диагностику каждого запуска. Сбой по памяти показывать как ограничение подхода, а не как результат измерения скорости.
5. **Измерения.** Отдельно измерять загрузку, преобразование, чтение, обучение, предсказание и полный цикл. Учитывать диск, CPU, RAM, холодный/тёплый кеш, конкурирующие задачи и одинаковое разбиение данных.
6. **Приёмка.** Поэтапно проверить 1, 10 и 100 ГБ на зафиксированной конфигурации машины: время, пик памяти/диска, корректность результатов, отмену, обрыв загрузки и перезапуск worker. Результаты такого теста, а не отсутствие ограничения в форме, подтверждают поддержку 100 ГБ.

Настройки Nginx сверены с официальной документацией: [размер запроса](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size), [потоковая передача запроса](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_request_buffering).

## Потоковая линейная регрессия Python

Решатель `streaming-centered-qr-sklearn-ols-v1` читает train и test серверными курсорами PostgreSQL. Размер блока рассчитывается из `ML_SKLEARN_MEMORY_MB` (512 МиБ по умолчанию) и числа признаков, максимум 4096 строк. Бюджет больше не используется для отклонения большого набора по оценке общего числа строк. Размер рабочего массива зависит от блока и числа признаков, а не от общего числа строк; это не жёсткая гарантия общего RSS процесса с библиотеками.

При обучении блоки [X,y] сводятся ортогональным QR-разложением. Для свободного члена сохраняются средние и поправка между блоками; матрица XᵀX не формируется. На компактной задаче применяется scikit-learn LinearRegression с восстановлением intercept. Отсечение сингулярных значений соответствует версии scikit-learn: для прежней политики учитывается исходное число строк, для 1.9+ используется стандартный tol. Результаты могут отличаться в пределах численной погрешности; плохо обусловленные задачи нужно оценивать отдельно.

Предсказания также рассчитываются блоками, временно записываются в дисковый CSV и передаются в PostgreSQL через COPY. Временный файл закрывается при нормальном завершении и исключениях. Чтение train входит в train_ns; чтение test и временная запись — в predict_ns; COPY — в persist_results_ns. Все эти операции входят в model_wall_ns, как и прежде. Режим выполнения показан на экране результатов и записан в JSON вместе с размером блока, числом обработанных train/test-строк и рангом.

Старые результаты остаются неизменными. Чтобы использовать новый адаптер, создайте новое сравнение через «Повторить / изменить настройки». Нулевое число пригодных пар теперь даёт неизвестный статус ограничений, а ошибки попыток показываются на основном экране.

Справочники: [LinearRegression](https://scikit-learn.org/stable/modules/generated/sklearn.linear_model.LinearRegression.html), [серверные курсоры psycopg](https://www.psycopg.org/psycopg3/docs/advanced/cursors.html#server-side-cursors).

### Проверка на полном пользовательском наборе, 3 ноября 2026

Сравнение `3ee8c385-1b25-4534-af96-8dc800fdeff1`: 1 000 000 строк, 50 признаков, 800 000 train / 200 000 test, пять измеряемых пар и одна прогревочная. Все 12 запусков успешны, пять пар приняты, исключённых пар нет. Исходные неуспешные эксперименты сохранены.

Наблюдаемый максимальный RSS дерева Python-исполнителя среди шести Python-запусков — 173,09 МиБ; медиана по измеряемым парам — 171,46 МиБ. Бюджет адаптера остался 512 МиБ, лимит контейнера worker — 1 ГиБ. Медианы RMSE: MADlib 0,3111701858848469, Python 0,31117018588484574. Медианы model_wall: MADlib 1,779 с, Python 13,497 с. Это локальные измерения на данном наборе, машине и состоянии кеша, не универсальное сравнение производительности.

Автотесты: 73 серверных (включая реальные PostgreSQL/MADlib, несколько блоков train/test, численное сравнение с плотным sklearn), 9 браузерных. Наборы около 100 ГБ пока не проверены: потоковый Python-адаптер устраняет зависимость RAM от полного числа строк, но дисковое хранение, импорт, длительные задания и возобновление ещё требуют отдельного масштабного тестирования.
