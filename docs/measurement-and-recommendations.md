# Ресурсы, парная статистика и рекомендации

Реализация предназначена для одного локального стенда PostgreSQL + MADlib и двух адаптеров линейной регрессии. Решение относится к конкретному comparison case, версии данных, разбиению и окружению. Разные размеры выборок и настройки intercept не объединяются в одного победителя.

## Установка и обновление

При первой инициализации bench volume функция мониторинга устанавливается автоматически. Для существующей БД её нужно применить отдельно; пересборка образа не запускает init-скрипты повторно:

```powershell
Get-Content deploy/bench/resources.sql -Raw | docker compose exec -T bench-db psql -v ON_ERROR_STOP=1 -U bench -d bench
docker compose stop api worker
docker compose up -d --build api worker
```

Миграция 0003 добавляет nullable experiments.analysis; старые результаты сохраняются. Для старых экспериментов без анализа endpoint возвращает analysis_not_published. Ресурсные измерения задним числом не восстанавливаются: создайте новую серию.

Функция criterion_monitor.snapshot читает только фиксированные файлы cgroup v2. У неё нет файловых аргументов или SECURITY DEFINER; PUBLIC не имеет прав вызова. В локальном Compose worker использует владельца bench. Для отдельных ролей администратор должен явно выдать USAGE схемы и EXECUTE функции. Не требуется Docker socket, privileged-контейнер или общий PID namespace.

## Что измеряется

| Область | CPU | Память | Что входит |
| --- | --- | --- | --- |
| python_process | Разница user+system CPU seconds | Максимум наблюдаемой суммы RSS | Executor, наблюдаемые дочерние процессы, sampler |
| bench_container | Разница cgroup cpu.stat usage_usec | Максимум наблюдаемой memory.current | Весь контейнер bench PostgreSQL: MADlib, ввод/вывод sklearn, фоновые процессы, кеш, мониторинг |

Определения счётчиков: [psutil](https://psutil.readthedocs.io/stable/index.html), [Linux cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html). RSS и memory.current имеют разные определения и в общий показатель памяти не складываются. CPU-budget max_cpu_seconds использует сумму CPU двух непересекающихся областей, включая фоновые и мониторинговые затраты.

Интервал по умолчанию — 100 мс, ML_RESOURCE_SAMPLE_SECONDS допускает 50–2000 мс. Начальная и конечная выборки окружают model_wall; периодические чтения идут по отдельному SQL-соединению, не на соединении обучения. Имя этого соединения привязано к attempt_id и участвует в отмене. Оценка качества, экспорт и подготовка общей выборки вне измеряемого окна. Каждая попытка сохраняет:

- resources.scopes: статус, CPU seconds, sampled peak и baseline памяти, число выборок/ошибок, лимиты CPU/RAM;
- window_seconds, interval_seconds, max_sample_gap_seconds, delayed_intervals, sampler_read_seconds;
- версии Python/PostgreSQL/адаптера, threadpoolctl и настройки work_mem, shared_buffers, parallel workers; политика кеширования uncontrolled_warm_cache.

Лимиты python_process описывают весь worker-контейнер, который делится с supervisor. Лимиты не означают индивидуальную квоту процесса. Монитор хранит потоковые агрегаты постоянного размера; не накапливает все сэмплы в памяти.

Пики памяти приближённые: краткий пик между сэмплами может быть пропущен. Для короткой операции иногда доступны только две граничные выборки. RSS общих страниц может учитываться у нескольких процессов. Недоступный счётчик, ошибка чтения, смена идентификатора контейнера/старта PostgreSQL или сброс CPU-счётчика дают status=unavailable и null вместо нуля. Для bench требуется ограниченный контейнер с приватным cgroup v2; обычный сервер без такого окружения не выдаётся за измеренный контейнер.

Мониторинг влияет на нагрузку; sampler_read_seconds показывает время чтений, но не является оценкой всего влияния мониторинга на скорость. Числа разных режимов мониторинга нельзя бесконтрольно смешивать. CPU контейнера включает чужую активность PostgreSQL, поэтому стенд должен быть выделенным, а контрольные серии запускаться без конкурирующих задач.

## Парная статистика

Внутри каждого case объединяются runs с одинаковым pair_id. Учитываются только пары с двумя успешными backend, одинаковым prepared manifest, положительными временами и конечным RMSE. Warmup не участвует. Сохраняются причины исключения пар и ID использованных runs/attempts.

Статистика возвращает отношения model_wall MADlib/sklearn для каждой пары, медиану отношения, медиану разницы времени, медианы времени обоих подходов и IQR отношений. Отношение больше 1 означает более медленный MADlib. 95% percentile bootstrap-интервал медианы строится по 4000 перевыборкам целых пар; seed детерминированно выводится из seed эксперимента и case_id. Это воспроизводимый pointwise-интервал: коррекция множественных сравнений разных cases не выполняется, возможная корреляция последовательных повторов остаётся ограничением метода.

## Политика выбора

Политика входит в неизменяемый spec и config_hash. Пример:

```json
{
  "kind": "benchmark",
  "dataset_version_id": "<UUID готовой версии>",
  "repeats": 5,
  "warmups": 1,
  "recommendation": {
    "policy_version": 1,
    "min_pairs": 5,
    "practical_speedup": 0.05,
    "quality_abs_tolerance": 0.000001,
    "quality_rel_tolerance": 0.01,
    "max_rmse": null,
    "max_model_seconds": null,
    "max_python_rss_bytes": null,
    "max_bench_memory_bytes": null,
    "max_cpu_seconds": null
  }
}
```

Сначала проверяется достаточность и полнота пар. Пропущенная/неуспешная пара или менее min_pairs полных пар дают inconclusive. Политика затем проверяет каждый измеряемый повтор: абсолютный предел RMSE, допустимое ухудшение RMSE относительно второго backend, время, наблюдаемые пики памяти по отдельным областям, сумму CPU seconds. Допуск качества: abs_tolerance + rel_tolerance × RMSE другого подхода. Предел памяти относится к наблюдаемому пику, не гарантирует отсутствие кратковременного превышения.

Если обязательный ресурс неизвестен, решение inconclusive. Если оба подхода нарушают условия — no_feasible_backend. Если подходит только один — он выбирается с причиной only_backend_meeting_constraints, без заявления о преимуществе скорости.

Если подходят оба, для practical_speedup=0.05:

- sklearn выбирается, когда нижняя граница интервала отношения больше 1.05;
- madlib — когда верхняя граница меньше 1/1.05;
- comparable — только когда весь интервал внутри [1/1.05, 1.05];
- пересечение границ даёт inconclusive.

Пять пар — минимальная рабочая настройка, а не гарантия достоверности. Отмена или прерывание не выдаёт положительную рекомендацию. Рекомендации не используются для подбора гиперпараметров по test-выборке.

## API и хранение

`GET /api/v1/experiments/{id}/results` сохраняет прежнюю сводку и добавляет analysis. `GET /api/v1/experiments/{id}/recommendation` возвращает сохранённый анализ с решениями по cases. `GET /api/v1/experiments/{id}/report` скачивает JSON с исходным spec, config_hash, политикой, статистикой и обоснованием. До публикации report возвращает 409.

Отчёт вычисляется worker при завершении последнего run и публикуется в той же защищённой lease/token транзакции, что и терминальный статус. API не пересчитывает вывод при чтении. Хранятся analysis_version, policy_version, input_sha256 и ссылки на конкретные попытки. Отдельные JSON-артефакты runs содержат ресурсы; итоговый отчёт формируется из сохранённого metadata JSON.

## Проверки

Unit-тесты проверяют парное resampling, детерминизм, преимущества каждого backend, практическую эквивалентность, широкий интервал, исключение warmup, недостающие пары, качество и ресурсные ограничения. Sampler тестируется на сбросах счётчиков, ошибках чтения и промежуточном пике памяти. Интеграционные тесты проверяют доступность двух областей на настоящих PostgreSQL/MADlib, публикацию отчёта и миграции.
